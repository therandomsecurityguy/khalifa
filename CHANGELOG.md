# Changelog

All notable changes to Khalifa.

## [Unreleased] - Observed-traffic hop citations and shift-left v2

### Added

- **Endpoint-level flow-log evidence**: the flow-log analyzer now runs a second, bounded aggregation alongside the per-interface totals — the top remote senders (`srcaddr`) per interface, ranked by bytes with a window function, capped at 5 per interface with a parsed-row cap and two Athena scans per run. The endpoints ride the existing `TrafficObservations` row (TTL unchanged); a failure in the endpoint query degrades to observations without citations, never a failed run. The collector deduplicates the top senders across an instance's interfaces (biggest first, capped at 5) onto `observed_endpoints`.
- **Hops cite observations**: attack paths carry per-hop `observedTraffic` citations (the engine maps each observed vertex to the 1-based hop that arrives at it, tolerantly), the explorer response and issue metadata include them, and the graph draws an "observed traffic from <address>" chip on the hop's target — so a path shows observed traffic on a specific hop, not just configured exposure.
- **Shift-left v2 in `risk:plan`**: IAM policy documents embedded in the plan (`aws_iam_policy` / `aws_iam_role_policy`) are parsed with the same parser the CIEM evaluator runs; a policy that newly grants `iam:PassRole` on `Resource: "*"` fails the gate as critical, and a wildcard `Action: "*"` is high. With a before-policy (plan `change.before`, or `--policy-before` with the new `--policy`) checks are a true diff — unchanged grants are not re-reported; conditions/SCPs are explicitly not evaluated. New `--helm-values values.yaml` flags an internet-facing ingress as high (plain enabled ingress: a medium note). Standalone policy files cover non-Terraform flows; the README documents the optional CI gate for all three inputs.

### Notes

- Still open from the re-review (`~/Documents/Testing/plans/2026-10-27-predictive-completion.md`): the long tail (UEBA breadth, EPSS/KEV enrichment, trust-center publication of projections, per-issue risk window/SLO).

## [Unreleased] - Freshness tempering across risk

### Changed

- **Likelihood is now five factors**: exposure, privilege, exploitability, reachability and **coverage** — the freshness of the graph the path was read from. The level and thresholds move to `packages/risk-engine/src/coverage.ts` as the single source of truth (the API's coverage statements grade with the same function), and the level scales the product deterministically: `aging` × 0.8, `stale` × 0.5. `unknown` (nothing collected yet, or a failed read) is deliberately not discounted — surfaces label it in words — so a fresh install is not punished while a provably old graph can never look confident.
- **The rule runner resolves coverage once per run** (newest SUCCEEDED `resource-inventory` `CollectionCoverage` completion, bounded at 5000 and failure-tolerant) and passes it to every path likelihood; each issue created or refreshed carries `metadata.coverageLevel`. The attack-path explorer and fix simulation temper their likelihoods the same way, and the explorer response now includes the coverage statement beside `truncated`.
- **The UI states coverage where results appear**: the explorer shows the statement note under its results, the fix panel under the edge ranking, the scenario card after a run, and the issue page labels the graph coverage the issue was scored against ("— the path likelihood is tempered down" for aging/stale).

### Notes

- Still open from the re-review (`~/Documents/Testing/plans/2026-10-27-predictive-completion.md`): observed-reachability v2 (remote endpoints, per-hop citation), shift-left v2 (IAM diff/Helm, CI wiring), and the long tail (UEBA breadth, EPSS/KEV, trust-center projections, per-issue risk window/SLO).

## [Unreleased] - Event-triggered recompute

### Added

- **Event-triggered policy evaluation**: the incremental collector now signals when a batch could have moved an escalation — any IAM node (`IamRole`, `IamUser`, `IamGroup`, `IamPolicy*`, `AccessKey`) or IAM edge (`TRUSTS`, `HAS_IAM_ROLE`, `ATTACHED_TO`, `MEMBER_OF`, `HAS_ACCESS_KEY`) marks the batch recompute-worthy — sending one best-effort message to a new `recompute` FIFO queue (`RECOMPUTE_QUEUE_URL`); a missing queue or a send failure never fails collection. The `recompute-worker` runtime command runs as a Deployment (rendered only when the queue is wired; policy-evaluator IRSA role plus receive/delete on the queue) that long-polls it and re-runs **the policy evaluator**, so escalation paths refresh within one incremental cycle instead of at the evaluator's scheduled hour; the hourly rule run still raises the corresponding issues. Two bounds keep the heavy job in check: the producer's FIFO deduplication id collapses a five-minute burst to one message, and the worker refuses to evaluate more often than `RECOMPUTE_MIN_INTERVAL_SECONDS` (default 900, chart `recomputeWorker.minIntervalSeconds`), deleting covered messages. A failed evaluation leaves messages for SQS redelivery and the queue's DLQ; the scheduled evaluator remains the backstop. Terraform creates the queue + DLQ, grants the incremental collector `SendMessage` and the policy-evaluator role receive/delete, and flows `recomputeQueueUrl` into the chart. The CDK path is not wired (documented).

## [Unreleased] - Outcome labels and coverage statements

### Added

- **Independent-detector corroboration**: once per run the rule runner resolves the resources Security Hub / GuardDuty findings point at (`DETECTS_ON`, one bounded read capped at 5000, truncation-aware and failure-tolerant) and records `metadata.independentFinding` on created and refreshed issues — true when one of the issue's resources was flagged too, false when the complete set missed it, absent when the set was unreadable, truncated, or the rule is those detectors themselves (RULE-018/029, where corroboration would be circular). A refresh clears the label when it can no longer be determined.
- **Real corroboration metric**: `GET /rules/quality` reads the label through the same bounded `StatusIndex` projections and publishes `corroborated`, `labeled`, and `corroborationRate = corroborated ÷ labeled` (null below five labelled issues) beside the dismissal rate; the Rules page gains a "Corroborated" column and explains that it does not change the verdict, which stays dismissal-based until the published data and a calibration decision support moving it. Auto-ticketing remains off per the P6 policy.
- **Coverage statements**: a shared helper grades the newest SUCCEEDED `resource-inventory` collection (`fresh` ≤ 8h, `aging` ≤ 72h, `stale` beyond, `unknown` when unreadable, failure-tolerant) and `/attack-paths/simulate` and `/attack-scenarios/:id` now return it with their counts; the issue fix panel and scenario results show it, and `risk:plan` states `plan-time` coverage with the same caveat its findings carry. The predictive surfaces no longer report counts without saying how fresh the graph they read is.

## [Unreleased] - ATT&CK mapping and adversary scenarios (P7b-2)

### Added

- **Curated MITRE ATT&CK mapping for the rule catalogue**: `attack-techniques.ts` (risk-engine) pins a reviewed technique set (ids, names, tactics) to every rule — the framework-citations pattern, with a test that every rule is mapped, every technique is known, and ids are well-formed, so drift fails CI. Nothing is executed and no AWS call is made; the "Adversary scenarios" page under Inventory runs one on demand and says so.

- P7b is now complete. ## [Unreleased] - Threat-intelligence matching (P7b-1)

### Added

- **Customer threat-intel matching**: `threat-intel-import` (runtime command; CronJob **suspended by default**, running as the rule-runner service account) imports plain S3 lists — one indicator per line, `#` comments, IPs (v4/v6) and 12-digit account ids — into a `ThreatIndicators` table with a TTL (`threat_intel_ttl_days`, default 90): freshness is the TTL, so a dropped indicator expires by itself, and invalid lines are skipped and counted in the log. Nothing calls the internet — the lists live in an account-owned bucket, and AWS's own managed reputation lists need no import because GuardDuty applies them (the findings they drive already feed RULE-018/RULE-029). Terraform creates the table, grants the rule-runner role read/write on it, and `s3:GetObject` on `threat_intel_list_bucket` when set; the list URIs, table name, and TTL flow through the chart config.
- **Matches change ranking**: the rule runner joins the store against the facts rules already match — an anomaly's `source_ip` and a trusted `ExternalAccount`'s account id — and a match adds a flat **+10 `threatIntelContribution`** to the risk score (additive like exploitability; a fact about the path, not a proportional strength). The issue records `threatIntelMatches` (type, value, source) and the issue page renders a "Threat intelligence" card; a refresh clears matches whose indicator is gone. **No auto-ticketing** for matched issues until `/rules/quality` shows the measured precision P6 requires, and the offline `risk:plan` gate is unaffected (no store to read, so it never claims a match). The lookup is failure-tolerant: a missing table or grant scores without it and logs a warning.

### Notes

- P7b-2 (TTP mapping to MITRE ATT&CK and graph-only adversary-emulation scenarios) remains open — it depends on the curated mapping table this phase deliberately left out; and the importer does not fetch external feeds (commercial/open IoC subscriptions would add the deployment's first outbound-internet component and licensing constraints on storing indicators).

## [Unreleased] - Observed reachability (P7a)

### Added

- **Observed reachability from VPC flow logs (optional, cost-gated)**: a new `flow-log-analyzer` runtime command aggregates ACCEPT flows per network interface — Athena over a `vpc_flow_logs` Glue table with partition projection (account/region/day) and the standard v5 fields, the account id taken from the partition — into a `TrafficObservations` DynamoDB table (one row per interface, TTL 30 days; window `flowLogAnalyzer.days`, default 7, max 31; at most 5000 interfaces per run, truncation logged). Terraform creates the table and the Glue table only when `flow_logs_bucket` is set (alongside the CloudTrail database it reuses), and the CronJob ships **suspended** by default: nothing runs or costs anything until an operator opts in. The collector reads the table during EC2 collection with the hub's own credentials (member-account credentials never touch it) and marks instances `traffic_observed` plus the latest observation time — the read is tolerant, so an absent table, a missing grant, or an analyzer that never ran simply means no observed traffic.
- **Observation in prediction and evidence**: path likelihood reachability is now observed AND configured — traffic observed on a workload proves reachability even when a restricted read (`lambda_exposure_restricted`, `collection_restricted`) left the configuration unknown, where it previously halved the factor. The issue page lists the latest observation as an "Observed traffic" fact beside the configured ones.
- **IAM**: the cloudtrail-analyzer role gains, only when flow logs are enabled, `TrafficObservations` writes, the flow-logs Glue table, and the bucket (plus optional KMS decrypt); the hub collector roles gain `dynamodb:BatchGetItem`/`GetItem` on the observations table. Helm values gain `flowLogAnalyzer` (with the standard NetworkPolicy egress component), `config.trafficObservationsTable`, and a `days` field on cron-job values.

### Notes

- Deferred: threat-intel enrichment (IOC feeds, TTP mapping) and adversary-emulation scenarios — both need a provider/format decision; source-ASN and time-of-day baselines from P4's note; and the CDK path does not create `TrafficObservations`, which the collector's tolerant read already handles.

## [Unreleased] - Rule quality and calibration (P6)

### Added

- **Per-rule quality report**: `GET /rules/quality` (Viewer) joins every rule's open/suppressed/resolved issue counts — read through the same bounded `StatusIndex` projections the issue summary uses — with the catalogue (name, team, severity, enabled, auto-ticket), and publishes `dismissalRate = suppressed ÷ handled` with a verdict: `reliable` under 20% over at least 10 closed issues, `noisy` at 50% or more, `mixed` between, `insufficient-data` before that. The rule runner and report keep no new state: suppression remains the recorded human judgement (reason, actor, expiry in the status history), and the report says plainly that the rate is a noise proxy, not precision. A `/rules` page under Risks renders the table with the thresholds explained, sorted noisy-first.
- **Calibration policy**: severity, scoring-weight, and auto-ticket changes cite the quality report as evidence; `RULE_QUALITY_*` thresholds are explicit constants so a change is an edit with recorded evidence, not a judgement call (also noted in AGENTS.md §2.3).

### Notes

- True precision/recall waits on outcome labels (GuardDuty/Security Hub findings and incident links joined to issues), and the first live calibration change (for example enabling auto-ticketing on a rule whose measured rate supports it) waits for production data — the report and thresholds are the mechanism that makes that change evidence-based rather than guessed.

## [Unreleased] - Behavioral baselines (P4)

### Changed

- **AccessDenied spikes are deviations from each principal's own baseline, not a fixed count**: the analyzer now pulls per-principal-per-IP-per-_day_ counts for the evaluation window plus a 30-day baseline and decides in code (testable against historical windows): a day flags when it reaches mean + 3 standard deviations of that pair's daily counts, with 10% of the mean as a floor on the spread (a perfectly steady principal is not flagged by +1) and an absolute floor of 10 events. A steady 25-denieds-per-day principal is no longer flagged at 26 (the old fixed threshold's false-positive class), and a quiet principal jumping to 12 — which the old threshold of 20 missed — is flagged. When fewer than 7 baseline days exist the previous fixed threshold applies (cold start). Each spike records `baseline_mean`, `baseline_stddev`, `baseline_days`, `basis` and `deviation`, and the principal's blast radius ranks it in scoring as before.
- **Secret-read "new source IP" is a true IP baseline**: the query joins the evaluation window's secret reads against the DISTINCT source IPs the principal used in the 30 days before it, left-joined, instead of the principal-first-seen proxy — an IP dormant for the whole baseline window and used again now counts as new, and the principal-age requirement is gone.

### Notes

- Deferred: source-ASN, time-of-day and first-seen-service baselines; an explicit deviation × blast-radius score term (the principal's blast radius already ranks deviating findings through the existing scoring factors); and provisioning a dedicated false-positive dashboard over live history.

## [Unreleased] - Trajectory forecasting (P3)

### Added

- **Three more trend series**: `openRiskScore` (the sum of every open finding's risk score, so a few criticals weigh more than many lows), `mttrHours` (mean hours from opening to resolution over issues resolved in the last 30 days, from one bounded page of the resolved status), and `adminPrincipals` (IAM users and roles the policy evaluator found to be admin — a leading indicator of blast-radius growth). The optional sources fail soft: an unreadable issue store or graph skips the day's point instead of failing the snapshot.
- **Explainable projections**: `forecastSeries()` (risk-engine) fits an ordinary least-squares line over the window and returns 7/30-day projections with a residual band and a confidence level (`high` = ≥14 points, tight residuals; `medium` = ≥7 points, moderate; otherwise `low`). `GET /trends/:metric` now returns `forecast` for every series with at least five points, and degrades the confidence a level — with the reason in `note` — when no runner pass recorded in two days or the window has three or more missing days (the trend-store equivalent of the compliance engine's `freshCoverage` gate).
- **Trends page projections**: the summary card renders the 7- and 30-day projections with their ranges, a confidence badge, the recent slope, and any staleness note; the metric picker gains copy for the three new series.

### Notes

- Deferred: trust-center publication of projections (needs the publishable discipline to cover them), a per-issue risk window from resolution history, SLO-burn thresholds, and an exposure-by-type series (a graph-wide group-by scan was judged too heavy for the hourly runner).

## [Unreleased] - Path likelihood and fix simulation (P2)

### Added

- **Path likelihood**: `pathLikelihood()` (risk-engine) returns an explainable 0..1 value — the product of exposure (internet 1 / cross-account 0.7 / internal 0.3), privilege (admin 1 … service-linked 0.4), exploitability (CVSS/10, +0.2 with a known exploit, capped at 1) and reachability (halved when a path vertex marks its exposure or state as unreadable). Unknown detail is a mid-value (0.5), not zero. It is persisted on issues (`metadata.likelihood` / `metadata.likelihoodFactors`), returned with every attack-path search result, and the explorer breaks score ties by it. `RiskScoreInput.reachabilityRestricted` reflects `lambda_exposure_restricted` / `collection_restricted` vertices.
- **Fix simulation**: `GET /attack-paths/simulate?ruleId=…` (Viewer + expensive-query limiter) re-runs the rule against the live graph — bounded at 200 matched paths and 10 ranked edges — and counts, per edge, how many of the matched paths traverse it, ordered by paths cleared then worst cleared likelihood. Nothing is mutated; removal is simulated over the returned paths. The issue page gains a "What removes these paths" panel that runs the simulation on demand and shows `clears N of M matched paths · worst likelihood P%` per fix, with empty and error states.

### Changed

- **`extractRulePath` is shared**: the driver-result parser moved to `rule-path.ts` and is exported (with the `RulePath` type), so the rule runner and the simulation API read the same result shape instead of duplicating it.

### Notes

- The roadmap's third P2 exit item — recomputing predictions immediately from incremental-collector deltas — remains open: incremental writes are picked up by the next scheduled evaluator run, and an event-triggered dispatch needs a scheduling surface decision.

## [Unreleased] - Exploitability (P1)

### Added

- **Amazon Inspector collection**: the collector's `inspector` stage writes one `Vulnerability` vertex per active CRITICAL or HIGH finding — the finding ARN as id, plus `cve_id`, `severity`, `cvss_base_score` (highest CVSS base score, falling back to Inspector's own score), `exploit_available`, `fixed_versions`, `inspector_score`, and first/last observed — and a `HAS_CVE` edge from the EC2 instance, Lambda function or ECR image the finding affects, matched by ARN against the vertices other stages collected. Inspector not being enabled records the stage `SKIPPED` with the reason rather than an empty success; findings are capped at 5000 per account/region with the truncation logged, and Inspector ARNs are excluded from tag lookups. New IAM read: `inspector2:ListFindings` on the spoke `SecurityGraphCollectorRole` policy and `khalifa-data` `PlatformRead` — a policy widening that requires the operator's confirmation before it is applied to member accounts (AGENTS.md §1.1).

### Changed

- **RULE-003 is live**: renamed "Internet-Exposed Workloads with Critical CVEs" and enabled. It matches a CRITICAL finding (CVSS 9.0+) on an internet-exposed EC2 instance, Kubernetes pod or Lambda function — on the workload itself or on a container image running on it — using edge steps so the drawn path keeps its edge labels. Auto-ticketing stays off until its firing rate is observed on real Inspector data; the REVIEWED_MAPPING entry (KH-VULN-1, "critical CVEs, on exposed workloads only") is unchanged.
- **Exploitability in the risk score**: `RiskScoreOutput.factors.exploitabilityContribution` (additive, at most 15 points: `cvss/10`, +0.2 when an exploit is known, capped at 1.0). Findings without CVE data keep exactly the scores they had — the zero-value CVSS weight the engine removed is not restored as a reweighting. The scoring factors and the audit trail explain it like every other factor.
- **UI**: `Vulnerability` facts (CVE, severity, CVSS, exploit known, fixed-in, Inspector score) render on the issue page's involved resources, and the scoring-factors card labels the new factor.

## [Unreleased] - Upstream parity (2026-10)

### Added

- **In-repo trust center**: `scripts/trust-center-sync` reads the sanitized publishable endpoint through the Cloudflare Access service token and writes `trust.config.json` + `build-meta.json` — statuses only, failing closed on `STALE`/`MISSING` records or transport errors. `trust-center/` renders those plus a hand-edited `site.config.json` into a dependency-free static site, deployed nightly to Cloudflare Pages by the `Trust center sync` workflow. No external fork; a tripwire rejects ARNs, account IDs, and access-key patterns before anything is published.
- **Batched auto releases**: the auto-tag job cuts a release only after `KHALIFA_RELEASE_MIN_COMMITS` commits (repository variable, default 10) have landed since the previous tag — merge commits bump minor, everything else patch — and dispatches the Release workflow itself when the optional `GH_KHALIFA` PAT is absent.
- **Complete EKS example**: `deploy/terraform/examples/complete` wires `khalifa-registry` → `khalifa-data` → `khalifa-eks` against an existing cluster, creates the External Secrets IRSA role for the runtime secret, and supports a two-phase apply (infrastructure and images first, then the release).
- **Terraform test coverage**: the `khalifa-eks` module and the complete example now have `terraform test` suites (release settings and values pass-through; chart-value composition, IRSA annotations, ExternalSecret mapping, ESO role scope), `khalifa-data` pins the `runtime_secret_name` output, and the deployment validation script runs them.
- **Upstream parity port**: the deployed fork's lambdas (runtime dispatcher, least-privilege sweep, DSPM scanner, IAM posture, GuardDuty findings, policy statements), CIEM/policy evaluator, SigV4 Neptune client, issue lifecycle and CIS reconciliation engine, API/UI surfaces, Helm chart, and Terraform modules were ported into this repository, with deployment identifiers scrubbed and configurable.

- **SOC 2 and ISO 27001 as mapped frameworks**: 26 curated requirements cite the canonical controls (`packages/risk-engine/src/framework-citations.ts`), and each requirement's status aggregates its mapped controls — any FAIL fails it, and manual or unevaluated controls keep it from passing. One canonical assessment pass serves every framework: mapped reports derive from the canonical ones (`derivedFrom`), write no evidence rows, and never duplicate an evaluator. The API lists them, and control pages link both ways ("Evidenced by" / "Cited by framework requirements").
- **Trust center publishes mapped frameworks**: `/compliance/reconciliation/publishable` now includes mapped requirements, gated on every mapped control being reconciliation-publishable (CIS) or assessed PASS/FAIL (Khalifa baseline report); the sync tool emits framework-tagged domains, and the in-repo site groups controls per framework. An unreadable baseline report leaves mapped frameworks unpublished rather than failing the CIS response.

- **AGENTS.md**: instructions for AI agents and automation — a secure AWS install workflow (identity verification before writes, secrets never leaving Secrets Manager, explicit human confirmation gates for destructive or widening changes, digest-pinned images, verification gates, rollback limits) plus the repository conventions agents must follow (load-bearing files, data hygiene, change discipline).

- **Continuous-monitoring proof on the trust center**: the publishable endpoint now publishes the staleness window it enforces (`maxAgeHours`, 24h), the sync records the assessment age (`recordAgeHours`), and the site's "Continuous monitoring" section states the assessment and publication cadence plus the automatic-unpublish rule — when the last assessment is older than the window, every framework leaves the page until assessments resume. A `monitoring.staleAfterHours` claim in `site.config.json` that contradicts the API's value fails the build, so the page cannot promise a window the API does not enforce.

- **Trust-center transparency sections**: `site.config.json` now drives security practices, subprocessors (with last-updated), public documents (link or request-access mailto), FAQs, a status-page link, and an RFC 9116 `/.well-known/security.txt` emitted when a security email is configured. The sync publishes a machine-readable questionnaire answer sheet (`questionnaire.json`, statuses only) and a rolling posture changelog (diffed from `posture-state.json`, newest first, capped at 20) rendered as "Recent posture changes". `SECURITY.md` documents the disclosure policy; OPERATIONAL section J.1 is the step-by-step go-live runbook.

- **PCI DSS and NIST SP 800-53 as mapped frameworks**: 26 further curated requirements join SOC 2 and ISO 27001 — PCI DSS v4.0 (11: network security, secure configuration, data protection, vulnerability management, access control, logging and monitoring) and selected NIST SP 800-53 Rev. 5 controls (15: AC-2/AC-6, AU-2/AU-6, CM-6, CP-9, IA-2/IA-5, RA-5, SC-7/SC-8/SC-12/SC-13, SI-2/SI-4). One canonical assessment pass serves all six frameworks; the trust center, questionnaire sheet, API, and UI pick them up automatically.

- **ReDoS-safe IAM wildcard matching**: `globMatch` (`packages/risk-engine/src/glob.ts`, re-exported for the lambdas as `lambdas/shared/glob.ts`) matches `*` and `?` iteratively — at most pattern length × text length steps — so IAM policy text can no longer make a generated regex backtrack exponentially.

- **`GraphNode.clearProperties`**: a writer can list properties to remove from an existing vertex because the source no longer reports them (a removed tag); the clear applies only when the write is newer, identity and reconcile bookkeeping (`id`, `arn`, `account_id`, `active`, `source_updated_at`, `collection_scope`, `collection_region`, `collection_run_id`) can never be cleared, and a key that is both set and cleared is rejected. `test/gremlin/Dockerfile` builds the hardened, pinned Gremlin 3.7.1 image, and `lambdas/graph-writer/graph-repository.graph.test.ts` (a new `graph-writer` project in `packages/risk-engine/jest.graph.config.js`, excluded from the default jest run) exercises chunked writes, reconcile, and clearing against a real server.

- **Collector coverage for role paths, instance profiles, Lambda exposure, and generic secrets**: every edge to an IAM role resolves through `roleVertexId` (`lambdas/collector/src/iam-ids.ts`), which strips the role's path, so a Lambda's `/service-role/` role ARN and path-carrying SSO trust principals no longer point at vertices that do not exist; EC2 instances get `HAS_IAM_ROLE` edges to the roles behind their instance profiles (`instance-profiles.ts`); Lambda functions record their function URLs and invoke policies (`lambda-exposure.ts`) as `function_url_auth_type`, `function_url_public`, `public_invoke_policy`, or `lambda_exposure_restricted` when the role may not read them; Secrets Manager secrets and SSM parameters are collected generically with age and rotation facts (`secret-ages.ts`). The spoke policy and `khalifa-data` `PlatformRead` gain `lambda:GetPolicy` and `lambda:ListFunctionUrlConfigs`.
- **Principal-aware resource policy statements**: statements now carry `principal_is_anyone`, `principal_account_ids`, and `principal_org_restricted` (the operators and condition keys that actually restrict to an organization), and an Allow statement to a foreign account's `:root` emits a `SHARES_WITH` edge.
- **Production-account marking**: `PROD_ACCOUNT_IDS` (validated 12-digit account IDs, default empty) sets `is_prod` on collected account vertices, and the inventory warns when a configured ID is not collected.
- **DSPM scanner SQS opt-in gate**: the event path scans only buckets tagged `dspm-scan=true` (memoized, fails closed), and `DSPM_SCAN_MODE=off` returns before any scan.

### Fixed

- **Graph chunks are no longer written twice**: a chained chunk yields one traverser, not one per element, so the old "returned N of M elements" check rejected every full chunk and re-ran it element by element — about 26 Neptune round trips instead of one, with duplicate-write conflicts (`Edge with id already exists`, `ConcurrentModificationException`) and writes outlasting the 30-second query timeout. Each chunk now aggregates the ids it wrote and ends in `cap()`, so one round trip covers the whole chunk; an unreadable result still falls back to element-by-element writes, and an edge the chain did not write (missing endpoint) is counted as skipped rather than failed.
- **Reconcile drops stale elements in batches**: a single drop of every stale element can outlast the query timeout (20 days of skipped cleanup would not finish). Reconcile now deletes at most `RECONCILE_BATCH_SIZE` (1000) elements per round, loops until a batch comes back short, and logs a warning when the batch cap is reached so the rest drops on the next run.
- **Edges to IAM roles with a path were dropped**: role vertices are `role/<RoleName>` without the path, but several stages built edges from the path-carrying ARN (`/service-role/` from Lambda functions, `/aws-reserved/` from SSO trust principals, duplicate `IamRole` vertices from the cross-account stage), so RULE-009 and the Lambda half of RULE-004 never matched those edges. Everything now goes through `roleVertexId`, and the cross-account stage points trust edges at the same vertex.
- **Exposure is not cleared when the network stages failed**: `is_internet_exposed` is written `true` or `false` every run, but a resource exposed only through a public subnet reads as unexposed when the subnets or internet-gateways stage failed. In that case (and when a Lambda's exposure could not be read) the collector now leaves the previous value in place, and an EC2 instance that lost its public IP clears `public_ip`.
- **Credential report stage no longer records an empty collection as complete**: with no current report the collector asked IAM to generate one and returned no rows while still marking the stage complete, so CIS 1.5 failed accounts whose root credentials were removed and 1.10/1.12 could pass on passwords that were never read. The stage now generates the report and waits up to 60 seconds for it, and fails when none becomes ready, leaving those controls unassessed instead of wrong.
- **KMS keys the collector cannot read are recorded as restricted stubs**: a key whose policy denies `DescribeKey` used to be skipped, so its account/Region passed controls with the key's rotation unknown. It is now written as a `KmsKey` stub with `collection_restricted: true` (readable keys set `false`).
- **Secret collections no longer fail the stage on denied reads**: a denied `DescribeSecret` or `GetResourcePolicy` keeps the secret from the `ListSecrets` entry with `collection_restricted: true`, and an SSM parameter ARN is built with exactly one slash.
- **ExternalAccount vertices are no longer re-scoped**: the scoping pass overwrote the trusted account in `account_id` (and one account's reconcile could drop another's trust), so RULE-006 could never match; ExternalAccount is now left unscoped like the Internet and AWS-managed-policy vertices.
- **Stale tags are cleared and ECR digest ARNs skipped**: tag-derived properties the latest successful tag lookup no longer returns are cleared (collector-set keys and keys written by other writers are kept), and `isTaggableArn` skips `repository/name@sha256:…` ARNs that made the Tagging API reject the whole batch.
- **One control's evaluation error no longer skips the rest of the run**: `runAssessment` saves its report and then threw on any control error, and `runAllAssessments` stopped there — one CIS 3.4 timeout ended both attempts after the CIS report, with no `KHALIFA_BASELINE` report, no mapped reports and no `CIS_RECONCILIATION` record. `runAllAssessments` now runs every framework, the mapped derivations, and returns the failures; the compliance runtime reconciles first and then fails the job, so the error is still seen.
- **CIS 3.4 timed out on Neptune**: a traversal joining every CloudTrail trail against every S3 bucket, re-run up to three times, hit the 30-second query timeout and reported `NOT_EVALUATED`. It now reads the trail bucket names, then which of those buckets lack access logging, as two short queries; bucket names are validated against S3's naming rules before they are interpolated into a query.
- **Security Hub passes where nothing was evaluated counted as passes**: Security Hub reports a control `PASSED` with reason `CONFIG_EVALUATIONS_EMPTY` when AWS Config evaluated no resources, and those made up most of the passes behind several requirements. Reconciliation now treats such a finding as no result (`SH_NO_RESULT`): a Khalifa FAIL for the same account/Region fills the gap as FAILED, a Khalifa pass never does, and a requirement with only such findings is blocked (`NO_SECURITY_HUB_RESULT`).
- **Stability no longer spans gaps in records**: a requirement's agreement carried forward from the previous record however old it was, so after the 2026-10-14 to 19 compliance failures several requirements showed 10 days of agreement, 5 of them with nothing compared. A previous record more than `MAX_RECORD_GAP_MS` (6 hours) old now restarts stability, and no agreement counts from before `AGREEMENT_EPOCH` (the first record after that gap).

- **Graph edges were never persisted**: edge upserts and edge reconcile set a Gremlin cardinality on edge properties, which Neptune rejects (`Property cardinality can only be set for a Vertex`). Every edge batch failed, so no traversal rule could match. Edges are now looked up by `khalifa_edge_id` alone (the label + endpoint scan is gone), and edges whose endpoints are not in the graph are skipped and counted (`skipped` in graph-writer responses and `skippedEdges` in collector logs) instead of failing the batch.
- **Graph-writer failure classes and collector retries**: transient Neptune failures (connection, conflict, timeout, and `MemoryLimitExceededException` while Neptune Serverless scales up from idle) return `503 {"retryable":true}`; anything else returns `500 {"retryable":false}`, and the shared Neptune client no longer treats Neptune status 500 (`InternalFailureException`) as retryable. Collectors retry a 503 or connection failure per batch with exponential backoff (`GRAPH_WRITER_RETRY_ATTEMPTS`, default 5) instead of re-scanning the account.
- **Account retries only for transient failures**: a denied API or collector-side error no longer re-scans the account three times and fails the Job. It is logged as `Collection degraded`, recorded on the `CollectionCoverage` vertex, and skips the account's reconcile. Only `THROTTLED`, `TIMEOUT`, and `TRANSIENT` stage failures are retried.
- **Collector stage failures that hit every account**: `DescribeFlowLogs` used the invalid `vpc-id` filter (`resource-id` is correct), failing the network stage wherever a VPC exists; local managed-policy ARNs were rebuilt from the name and lost the path (`/service-role/`), so `GetPolicyVersion` failed the IAM stage; a missing account password policy raises `NoSuchEntityException`, not `NoSuchEntity`; KMS keys whose key policy denies the collector (AWS-managed keys) are skipped instead of failing the stage; tag lookups only include ARNs the Resource Groups Tagging API accepts (no IAM `:root`, `:password-policy`, AWS-managed policies, or synthetic vertices); Security Hub findings truncate at 500 and set `findings_truncated` instead of throwing.
- **`s3:GetEncryptionConfiguration`**: `s3:GetBucketEncryption` is not an IAM action, so `GetBucketEncryption` was denied in every account. Fixed in the spoke template and the home-account IRSA policies. The spoke managed policy is now `CollectionPolicyV2` so StackSet instances still on V1 are identifiable.
- **Neptune Serverless floor**: `khalifa-data` exposes `neptune_min_capacity` (default 2.5 NCU) and `neptune_max_capacity` (default 8). At 1 NCU the first writes of every collector burst failed with `MemoryLimitExceededException`.
- **Rule result size**: every rule projects `path()` to the properties the runner reads (`arn`, name, and scoring inputs) instead of `valueMap(true)`, which carried whole policy documents through Neptune.
- **Explicit collection accounts skip Organizations ListAccounts**: `COLLECTION_ACCOUNT_IDS` is used as-is. Member-account hub-and-spoke collection no longer requires Organizations delegated admin.
- **Graph-writer Gremlin 3.8 remote bind**: use `traversal().withRemote(...)`. `graph.traversal().withRemote` is not a function in 3.8, so org-collector POSTs returned 503.
- **Home-account collector IRSA reads**: org-collector and incremental IRSA get the same collection actions as `SecurityGraphCollectorRole`. Home uses ambient credentials and has no spoke role.
- **Neptune ingest contention**: RULE-005 no longer uses `.times().until()` (two RepeatSteps, InternalFailure). Org-collector / compliance / rule-runner crons run every 4h, staggered. Graph-writer retries `ConcurrentModificationException` per vertex/reconcile and writes at concurrency 2. Collector fan-out matches that.

### Changed

- **Runtime secrets out of Lambda environment variables (D2 part 2)**:
  - `COLLECTOR_EXTERNAL_ID` is no longer a Lambda environment variable. The CDK stack creates a `khalifa/runtime` secret (generated, as the Terraform module already does) and passes only its ARN (`COLLECTOR_EXTERNAL_ID_SECRET_ARN`); the collectors resolve the value from Secrets Manager, falling back to the environment so the container runtime that receives it via External Secrets keeps working
  - The IAM `sts:ExternalId` condition refers to the secret through a CloudFormation dynamic reference, so the value never appears in the template. The reference must be a literal string: interpolating a token made CDK emit an `Fn::Join`, which CloudFormation does _not_ treat as a dynamic reference and would have passed the literal braces as the external ID. Both roles declare a dependency on the secret so the policy is not created before the secret has a value
  - Dropped the legacy Helm `collection.externalId` and `graphWriter.token` values and the `collection-secret.yaml` template. The chart now requires `externalSecrets.targetName`, which is already how the EKS deployment gets `COLLECTOR_EXTERNAL_ID` and `GRAPH_WRITER_TOKEN` (the validation script asserts this contract)
  - `incremental-collector` declares `@aws-sdk/client-secrets-manager`, which the shared credential resolver now uses

- **Deletion protection for the Terraform DynamoDB tables (closes the gap left by D2 part 1)**: all six tables now set `deletion_protection_enabled`. The module previously had no deletion protection, and the plan's note that "Terraform already does this" was not accurate, so the earlier D2 change only hardened the CDK tables, which production does not use. The module test now asserts deletion protection and point-in-time recovery on every table.
- Note: the module already declares `point_in_time_recovery { enabled = true }`, but the deployed `khalifa-*` tables report PITR disabled, so an apply is still required to reconcile that drift.

- **Data protection and DSPM read scoping (D2 of the remediation plan, part 1)**:
  - Every CDK DynamoDB table now has point-in-time recovery and deletion protection, matching the Terraform module. Previously a stack operation or a bad delete could destroy posture history
  - The DSPM scanner's `s3:GetObject` is scoped to an approved bucket allowlist (`DSPM_BUCKET_ALLOWLIST` / `dspm_bucket_allowlist`) instead of `arn:aws:s3:::*/*`. The scanner's own `dspm-scan` tag gate remains as defence in depth, but it is the allowlist that bounds what object reads can reach. Bucket tags cannot do this: S3 objects are not matched by `aws:ResourceTag`, and the opt-in tag lives on the bucket. `s3:ListAllMyBuckets` is split out because it cannot be resource-scoped. An empty allowlist grants no object read at all (bucket-level listing remains), so content scanning requires configuring the allowlist; it never falls back to every bucket
  - Removed the CDK Neptune auth secret. It became unreferenced when the CIEM lambdas moved to SigV4 (D1) and nothing could read it
  - The CDK tables are now encrypted with a customer-managed KMS key with rotation enabled, instead of the AWS-owned default. Because DynamoDB requires the calling principal to hold `kms:Decrypt`/`GenerateDataKey`, and `grantReadWriteData` does not add them, the key is granted explicitly to every table consumer (least-privilege-sweep, cloudtrail-analyzer, risk-engine, compliance-engine)
