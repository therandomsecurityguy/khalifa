# Changelog

All notable changes to Khalifa.

## [Unreleased] - Upstream parity (2026-10)

### Added

- **In-repo trust center**: `scripts/trust-center-sync` reads the sanitized publishable endpoint through the Cloudflare Access service token and writes `trust.config.json` + `build-meta.json` — statuses only, failing closed on `STALE`/`MISSING` records or transport errors. `trust-center/` renders those plus a hand-edited `site.config.json` into a dependency-free static site, deployed nightly to Cloudflare Pages by the `Trust center sync` workflow. No external fork; a tripwire rejects ARNs, account IDs, and access-key patterns before anything is published.
- **Batched auto releases**: the auto-tag job cuts a release only after `KHALIFA_RELEASE_MIN_COMMITS` commits (repository variable, default 10) have landed since the previous tag — merge commits bump minor, everything else patch — and dispatches the Release workflow itself when the optional `GH_KHALIFA` PAT is absent.
- **Complete EKS example**: `deploy/terraform/examples/complete` wires `khalifa-registry` → `khalifa-data` → `khalifa-eks` against an existing cluster, creates the External Secrets IRSA role for the runtime secret, and supports a two-phase apply (infrastructure and images first, then the release).
- **Terraform test coverage**: the `khalifa-eks` module and the complete example now have `terraform test` suites (release settings and values pass-through; chart-value composition, IRSA annotations, ExternalSecret mapping, ESO role scope), `khalifa-data` pins the `runtime_secret_name` output, and the deployment validation script runs them.
- **Upstream parity port**: the deployed fork's lambdas (runtime dispatcher, least-privilege sweep, DSPM scanner, IAM posture, GuardDuty findings, policy statements), CIEM/policy evaluator, SigV4 Neptune client, issue lifecycle and CIS reconciliation engine, API/UI surfaces, Helm chart, and Terraform modules were ported into this repository, with deployment identifiers scrubbed and configurable.

- **SOC 2 and ISO 27001 as mapped frameworks**: 26 curated requirements cite the canonical controls (`packages/risk-engine/src/framework-citations.ts`), and each requirement's status aggregates its mapped controls — any FAIL fails it, and manual or unevaluated controls keep it from passing. One canonical assessment pass serves every framework: mapped reports derive from the canonical ones (`derivedFrom`), write no evidence rows, and never duplicate an evaluator. The API lists them, and control pages link both ways ("Evidenced by" / "Cited by framework requirements").
- **Trust center publishes mapped frameworks**: `/compliance/reconciliation/publishable` now includes mapped requirements, gated on every mapped control being reconciliation-publishable (CIS) or assessed PASS/FAIL (Khalifa baseline report); the sync tool emits framework-tagged domains, and the in-repo site groups controls per framework. An unreadable baseline report leaves mapped frameworks unpublished rather than failing the CIS response.

- **AGENTS.md**: instructions for AI agents and automation — a secure AWS install workflow (identity verification before writes, secrets never leaving Secrets Manager, explicit human confirmation gates for destructive or widening changes, digest-pinned images, verification gates, rollback limits) plus the repository conventions agents must follow (load-bearing files, data hygiene, change discipline).

- **Continuous-monitoring proof on the trust center**: the publishable endpoint now publishes the staleness window it enforces (`maxAgeHours`, 24h), the sync records the assessment age (`recordAgeHours`), and the site's "Continuous monitoring" section states the assessment and publication cadence plus the automatic-unpublish rule — when the last assessment is older than the window, every framework leaves the page until assessments resume. A `monitoring.staleAfterHours` claim in `site.config.json` that contradicts the API's value fails the build, so the page cannot promise a window the API does not enforce.

- **Trust-center transparency sections**: `site.config.json` now drives security practices, subprocessors (with last-updated), public documents (link or request-access mailto), FAQs, a status-page link, and an RFC 9116 `/.well-known/security.txt` emitted when a security email is configured. The sync publishes a machine-readable questionnaire answer sheet (`questionnaire.json`, statuses only) and a rolling posture changelog (diffed from `posture-state.json`, newest first, capped at 20) rendered as "Recent posture changes". `SECURITY.md` documents the disclosure policy; OPERATIONAL section J.1 is the step-by-step go-live runbook.

### Changed

- **Releases no longer require AWS configuration**: digest-only image publishing activates only when `KHALIFA_AWS_ROLE_ARN` and the ECR repository variables are set; without them a release ships Lambda archives, the Helm chart, the `khalifa-eks` bundle, the SBOM, and checksums, recording `published: false` in `release-manifest.json`.
- **`khalifa-registry` takes `github_repository`** (plus an optional `github_oidc_subject_prefix`) instead of hardcoding the publishing repository, and the S3 access-log destination is implemented with inline module resources rather than a private external module.
- **Helm schema allows `mountIn: dspmScanner`**, matching the scanner template, so the DSPM scanner can receive the graph-writer token through External Secrets.
- **Compliance documentation corrected**: the evaluated frameworks are CIS AWS Foundations v3.0.0 (47 controls) and the Khalifa baseline (41 controls), 55 automated; the README no longer claims SOC 2 or ISO 27001 evaluations.

## [Unreleased] - Phase 0

### Added

- **Trust-center publishable endpoint**: `GET /compliance/reconciliation/publishable` returns only the CIS requirements in the latest `CIS_RECONCILIATION` record that are publishable and allowlisted, as `{requirement, title, section, status}`, with `status` `OK`, `STALE` or `MISSING` for the record. A `STALE` record, one older than 24 hours, or no record at all lists nothing; a read error is a 500, never an empty list. No account IDs, Regions, counts or disagreements leave Khalifa. Its only caller is the trust-center sync, authenticated by a Cloudflare Access service token whose client ID is `reconciliation.trustCenterSyncClientId` (`TRUST_CENTER_SYNC_CLIENT_ID`). That token's signed Access JWT has no email, so it gets no role and every other route still refuses it; staff roles, Admin included, cannot call the endpoint. Empty by default, so nothing is accepted.
- **CIS reconciliation against Security Hub**: at the end of each compliance run, Khalifa reads Security Hub's CIS v3.0.0 control findings through the audit account's read-only `khalifa-securityhub-reader` role and compares them with its own CIS report per requirement × account (× region for regional controls). Outcomes are `AGREE_PASS`, `AGREE_FAIL`, `DISAGREE`, `KHALIFA_AGGREGATE_ONLY` (Khalifa reports only an org-wide count; an org-wide PASS that Security Hub fails is still a `DISAGREE`), `KHALIFA_NO_RESULT` and `SH_NO_RESULT`. Each run stores a `CIS_RECONCILIATION` record in the reports table with the disagreeing accounts and, per requirement, how long it has agreed without a break. A requirement is publishable only after `reconciliation.minAgreementDays` (default 5) of agreement and only if it is in `reconciliation.publishAllowlist` (default empty, so nothing is). If Security Hub can't be read, the record is `STALE`: nothing is publishable and every agreement restarts. The compliance run itself never fails because of reconciliation. Disabled until `reconciliation.securityHubRoleArn` is set; `khalifa-data` grants the compliance role `sts:AssumeRole` on that ARN only when `securityhub_reader_role_arn` is set. The Security Hub control → CIS requirement map is checked against the stored source-of-truth page by a test.
- **Per-account CIS evidence records which accounts were assessed**: per-account and per-account-region controls now include `assessedAccounts` / `assessedAccountRegions` alongside the failing ones, so an account missing from the failures can be told apart from one that wasn't evaluated.

### Changed

- **22 CIS controls report per account or per account and Region**: these controls counted violations across the whole graph, so reconciliation could only mark them `KHALIFA_AGGREGATE_ONLY` and never compare them with Security Hub, which scopes them to the account or Region. Each now fails the accounts (1.4, 1.10, 1.12, 1.14, 1.15, 1.17, 1.22, 2.1.2, 3.2, 3.4, 3.5) or account/Regions (1.20, 2.3.1-2.3.3, 3.6, 3.7, 5.1-5.4, 5.6) with a violating resource, among those whose collection stage completed, and keeps the violation count as `violations`. An organization trail is one vertex for every member, so a failing one fails every assessed account for 3.2, 3.4 and 3.5. 1.12 checks access keys and console passwords in one query. 1.15 now waits for AWS-managed policy vertices before failing anything: per account, a zero elsewhere is no more trustworthy than before.
- **Issue page shows what made each resource match**: the Involved resources card listed only each resource's type, name and account ID; the facts behind the match were visible only by reading the graph. Each resource now shows its facts from the latest collection, read from the attack-path vertices the page already receives: for an access key its status, age and last use; for a security group rule its direction, protocol, ports and source; for a finding its title, severity and states; and so on per resource type, with a generic fallback for types without a template. The facts the rule's query matched on are highlighted with the rule's condition beside them, the account shows its name, and a resource that has left the graph says so. The card notes when the values were collected.
- **Issues list newest first**: the list had no creation order. With no status or several statuses `GET /issues` scanned the table in no order, and with one status or rule it used `StatusIndex` / `RuleIdIndex`, sorted by `updatedAt`, which the rule runner rewrites on every run. A new `StatusCreatedIndex` (`status`, `createdAt`) is read per status in creation order and merged, so the order holds across statuses and Load more. `GET /issues` takes `order=desc` (default) or `asc`; a single rule is now a filter on that index rather than a `RuleIdIndex` query. The page token is checked against the query's order and statuses and the exact index key shape before it is used. Until the index exists the first page falls back to the previous order. The Created column header toggles newest or oldest first and survives Clear filters. Apply the index (Terraform `khalifa-data`, or the CDK stack) and wait for it to be `ACTIVE` before deploying the API.
- **Issues page summary and filters**: the four severity tiles are replaced by one summary card showing total issues split into open, suppressed, and resolved, and a severity bar. Clicking a status or severity filters the list, and each side recounts for the other's selection. It reads the new `GET /issues/summary`, which counts every severity and status through `StatusIndex`, projecting only `severity`. The filter bar is gone: Rule and Team have multi-select funnels in their column headers, the Issue column shows only the title, and the Resources column is removed. `GET /issues` accepts several `ruleId` values (up to 50). The nav bar and card headers are tinted blue and inset panels light orange.

### Fixed

- **CIS 1.5 passes accounts whose root user has no credentials**: Security Hub IAM.9 passes "if root user credentials aren't present in the account", as with AWS Organizations central root access. Khalifa failed those accounts because the credential report's `password_enabled` was stored as `value === 'true'`, so a removed root password (`false`) looked the same as a normal one (`not_supported`). The collector now records `root_credentials_present` on the root row (no password, access key or signing certificate means false), and 1.5 passes an account whose root has MFA or no credentials. Found by the reconciliation: 9 accounts disagreed with Security Hub.
- **CIS 1.4 and 1.5 read the root user from the account vertex**: list-accounts writes `arn:aws:iam::<account>:root` as an `AwsAccount` before the IAM stage writes root posture (`mfa_enabled`, `HAS_ACCESS_KEY`) to the same id, and an upsert never changes a label. Both controls matched `IamUser` only, so 1.5 failed all 25 accounts (Security Hub IAM.9 passes the audit account, whose `AccountMFAEnabled` is 1) and 1.4 could not see a root access key. They now match `hasLabel('IamUser', 'AwsAccount')`.
- **Accounts configured by ID now carry their Organizations name**: with `COLLECTION_ACCOUNT_IDS` set, the inventory wrote each `AwsAccount` vertex with no `name`, so the attack path rail, graph bands, and `GET /accounts` showed bare 12-digit IDs. The organization inventory now calls `ListAccounts` once per run and copies the name of every listed account it finds. Nothing else changes: listed accounts are still collected as `ACTIVE` whatever Organizations reports, an account it does not return stays nameless, and a hub that may not list accounts logs a warning and keeps collecting without names. The incremental collector does not make the call.
- **Issue status changes record who, when, and why; suppressions expire**: the suppress route read a `reason` and then dropped it, so a suppression kept no reason, actor, or date, never expired, and a suppressed issue stayed suppressed even after its problem was fixed. Resolution kept no time or reason either. Every status change now goes through one conditional write that pins the status it read and appends `{from, to, at, by, reason}` to `statusHistory` (newest 50 kept). Resolving stamps `resolvedAt` and `resolvedReason` (`No longer matched by RULE-xxx`). Suppressing requires a reason (1-500 characters) and an `expiresAt` within 90 days, takes the actor from the verified token rather than the body, and stores `suppression` with the severity at the time. On each run the rule-runner resolves suppressed issues that stopped matching, and reopens a suppression once it expires or when the issue's severity rises above the suppressed severity. Suppressions made before this release have no `suppression` record and reopen on the first run. The issue page shows a status badge, a Status card with the details and history, and requires a reason and a duration (7, 30, or 90 days) to suppress; the issue list gains a Status column with the resolved date or suppression expiry. Issues resolved before this release show that their resolution time was not recorded.
- **Posture trends record issue churn and only list metrics that are written**: the rule-runner now records `issuesCreated` and `issuesResolved` per day. `PostureTrendStore.increment()` uses `UpdateItem` with `ADD`, so every run's count is summed into the day's row instead of the last 4-hour run replacing it. `exposedResourcesByType` and `failedControlsByFramework` are removed from the API and UI because nothing ever wrote them. `openIssuesBySeverity` is still the total open count, and each run now also stores that total split by severity in the row's `sample`. The API returns only those four counts, as `bySeverity`. The Trends page lists the newest day first. On Open issues it shows each severity's change from the previous day next to the total's change (the first day with a split shows counts; earlier days show none). It colours deltas by each metric's direction (more resolved issues is green), names the baseline and comparison dates instead of "start" and "yesterday", draws no bar for a zero day, and no longer says lower is better on every series. The CDK risk engine role gains `dynamodb:UpdateItem` on the trends table; the Terraform role already had it.
- **Reconcile failed every account that had stale elements**: the drop traversal ended in `iterate()`, which the gremlin 3.8 driver encodes as a `discard` step that Neptune's TinkerPop 3.7 engine rejects (`InvalidParameterException: Unable to find Traversal steps for the graph operator: discard`). The graph-writer returned a permanent 500, so since v1.36.0 the org-collector Job failed for the 17 accounts whose previous run had retired anything (`17 operations failed: Graph writer returned 500`). The drop now terminates with `next()`; a test forbids `iterate()` on the repository's traversals.
- **RULE-018 exceeded the chart's Neptune result limit**: `config.neptuneMaxResults` defaulted to 1000 while RULE-018 produces one path per active critical or high Security Hub finding on an exposed resource (814 on 2026-09-19 and growing), and the runner rejects an over-limit result outright, failing every scheduled rule-runner run. The default is now 10000, the schema maximum.
- **Attack path explorer default depth is 4**, the cap for Viewers since v1.38.0; the previous default of 6 was rejected on the first click for every Access user.
- **Resource links and issue attack paths in the API**: `extractVertex` let a collector node's `id` property (the resource's short name) overwrite the `T.id` ARN, so the resource explorer linked to `/resources?arn=<name>` and the API rejected it, and issue attack paths drew nodes whose ids never matched their edges (no arrows, no crossings). Token keys now win; a string `id` stays a property. Issue detail looks each path vertex up once instead of twice per segment, and resource and neighbour lookups use the vertex id instead of an `arn` property scan.
- **Rules wait out Neptune memory-limit storms**: Neptune Serverless rejects every path query with `MemoryLimitExceededException` for a minute or two after a burst of heavy ones (the same RULE-018 query answered in 0.5 s, failed instantly five times in a row, then answered in 0.5 s again; capacity stayed at 16 NCU), which failed the 01:30Z rule-runner on both attempts. The shared client's sub-second retries cannot outlast that, so the runner now re-runs a rule's query after 5 s, 15 s, 30 s, 60 s, and 60 s before recording the failure; non-retryable errors still fail immediately.
- **Collector crashed on large accounts**: aggregating a service's results with `nodes.push(...result.data.nodes)` threw `Maximum call stack size exceeded` once an account produced a few hundred thousand nodes (prod and qa), which failed the whole org-collector Job on every schedule and retried it into the rule-runner's window. Growable lists are appended with a loop everywhere (collector, pagination, rightsizer, DSPM samplers). The runtime now logs the account, attempt, and stack when an account's collection throws, and the stack of the final failure.
- **Reconcile now runs over HTTP and removes stale elements**: the collector's per-run reconcile was stripped client-side and refused server-side, so nothing written by an earlier run was ever retired. `/mutations` now accepts a validated `reconcile`, and the repository deletes the vertices and edges in the scope that the completed run did not re-emit (nothing consumed the previous `active` / `tombstoned_at` markers, and rules kept matching retired resources). Equality filters lead the reconcile traversal, most selective first.
- **Rule paths carry edge labels**: rule templates traverse `outE(...).inV()` / `inE(...).outV()` instead of `out()` / `in()`, and the runner splits the alternating path into vertices and edges, so `pathSummary.edgeType` is the edge label rather than the next vertex's label.
- **S3 stage survives a bucket-policy denial**: a bucket whose policy denies the collector is recorded with `configuration_access_denied: true` instead of failing every bucket in the account.
- **Chart**: `dspm-scanner` is a valid NetworkPolicy component and the graph-writer ingress admits it, so environments no longer need to filter it out of `egressCidrs`; it is removed from the Neptune egress list it never used.
- **DSPM scanner**: `tagged-only` now gates sampling: only buckets tagged `dspm-scan=true` are read (`GetBucketTagging`, granted to the IRSA role and the CDK role). The IRSA role gains `lambda:ListFunctions`, which the Lambda environment scan always needed; the CDK grants gain the object-level S3 resource form, `macie2:DescribeBuckets`, and `lambda:ListFunctions`.
- **API graph reads showed `unknown` labels and no names**: the API submits bytecode through the shared Neptune client, and for bytecode the driver returns `Traverser` wrappers (`{ object, bulk }`) that the parser then read as the vertex. The shared client now unwraps traversers (expanding `bulk`), which fixes the resource explorer, issue-detail attack paths, neighbours, trust graph, and escalation paths.
- **Attack Path Explorer failed on every search**: both path queries used `.until(...).times(...)`, which TinkerPop 3.7 parses as two `repeat` steps (`The repeat()-traversal was not defined`). They now use one `until(or(target, loops().is(gte(max))))` guard, the pattern RULE-005 already uses.
- **Risk rules never produced issues from real Neptune results**: the runner read each path element as a plain object, but the Gremlin driver delivers `path().by(valueMap(true, …))` elements as `Map`s keyed by the `T.id` / `T.label` enum values with list-wrapped values, so every vertex came back without an id or label and was silently dropped as a non-resource. The runner now reads that shape (and the legacy plain-object shape), unwraps single-valued lists, and rejects a path whose vertex has no id instead of skipping it.
- **Read queries retry `MemoryLimitExceededException`**: the shared Neptune client treats it as transient, like `ConcurrentModificationException`; on Neptune Serverless it surfaces sporadically for reads while the collector is writing.
- **Transient Neptune write failures are retried per element**: `MemoryLimitExceededException` joins `ConcurrentModificationException` and `ConstraintViolationException` in the graph-writer's per-vertex / per-edge retry (6 attempts, 50 ms doubling). Measured on Neptune Serverless at 16 NCU, roughly one in twelve concurrent tiny writes fails this way and the same write succeeds on retry; previously one such failure anywhere in a batch failed the whole batch, the collector replayed the batch up to five times, and repeated hits re-scanned the account.
- **Neptune Serverless defaults**: `khalifa-data` now defaults to 16 min / 32 max NCU. At the previous 2.5 NCU default an idle cluster rejected single-vertex writes with `MemoryLimitExceededException` and `ConcurrentModificationException`; writes only succeeded once the instance had scaled to 8 NCU or more, and failed again for a few minutes on every scale transition.
- **Graph writes use deterministic ids**: vertices are created with `T.id` = ARN and edges with `T.id` = `khalifa_edge_id`, and every lookup is an id step. The edge create branch previously resolved endpoints with a mid-traversal `V().has('arn', …)`, which Neptune's TinkerPop engine cannot serve from the index, so each edge scanned the whole vertex set twice (measured 700 ms+ per lookup versus 20 ms by id) and saturated Neptune Serverless with `MemoryLimitExceededException` and timeouts. `ConstraintViolationException` from a concurrent create of the same id is retried like `ConcurrentModificationException`. Graphs written by earlier releases carry random vertex ids and must be dropped once before this release collects.
- **Graph-writer failures name the element**: `Graph write failed for vertex <label> <arn>: …` / `edge <label> <from> -> <to>: …`, with the Neptune status code preserved for classification.
- **Collector merges nodes emitted by more than one stage** (IAM users and roles) before exposure, tagging, and writing, so a vertex is upserted once per batch and the Tagging API no longer rejects the request as a duplicate ARN.
- **Graph edges were never persisted**: edge upserts and edge reconcile set a Gremlin cardinality on edge properties, which Neptune rejects (`Property cardinality can only be set for a Vertex`). Every edge batch failed, so no traversal rule could match. Edges are now looked up by `khalifa_edge_id` alone (the label + endpoint scan is gone), and edges whose endpoints are not in the graph are skipped and counted (`skipped` in graph-writer responses and `skippedEdges` in collector logs) instead of failing the batch.
- **Graph-writer failure classes and collector retries**: transient Neptune failures (connection, conflict, timeout, and `MemoryLimitExceededException` while Neptune Serverless scales up from idle) return `503 {"retryable":true}`; anything else returns `500 {"retryable":false}`, and the shared Neptune client no longer treats Neptune status 500 (`InternalFailureException`) as retryable. Collectors retry a 503 or connection failure per batch with exponential backoff (`GRAPH_WRITER_RETRY_ATTEMPTS`, default 5) instead of re-scanning the account.
- **Account retries only for transient failures**: a denied API or collector-side error no longer re-scans the account three times and fails the Job. It is logged as `Collection degraded`, recorded on the `CollectionCoverage` vertex, and skips the account's reconcile. Only `THROTTLED`, `TIMEOUT`, and `TRANSIENT` stage failures are retried.
- **Collector stage failures that hit every account**: `DescribeFlowLogs` used the invalid `vpc-id` filter (`resource-id` is correct), failing the network stage wherever a VPC exists; local managed-policy ARNs were rebuilt from the name and lost the path (`/service-role/`), so `GetPolicyVersion` failed the IAM stage; a missing account password policy raises `NoSuchEntityException`, not `NoSuchEntity`; KMS keys whose key policy denies the collector (AWS-managed keys) are skipped instead of failing the stage; tag lookups only include ARNs the Resource Groups Tagging API accepts (no IAM `:root`, `:password-policy`, AWS-managed policies, or synthetic vertices); Security Hub findings truncate at 500 and set `findings_truncated` instead of throwing.
- **`s3:GetEncryptionConfiguration`**: `s3:GetBucketEncryption` is not an IAM action, so `GetBucketEncryption` was denied in every account. Fixed in the spoke template and the home-account IRSA policies. The spoke managed policy is now `CollectionPolicyV2` so StackSet instances still on V1 are identifiable.
- **Neptune Serverless floor**: `khalifa-data` exposes `neptune_min_capacity` (default 2.5 NCU) and `neptune_max_capacity` (default 8). At 1 NCU the first writes of every collector burst failed with `MemoryLimitExceededException`.
- **Rule result size**: every rule projects `path()` to the properties the runner reads (`arn`, name, and scoring inputs) instead of `valueMap(true)`, which carried whole policy documents through Neptune.
- **Explicit collection accounts skip Organizations ListAccounts**: `COLLECTION_ACCOUNT_IDS` is used as-is. Member-account hub-and-spoke collection no longer requires Organizations delegated admin.
- **Graph-writer Gremlin 3.8 remote bind**: use `traversal().withRemote(...)`. `graph.traversal().withRemote` is not a function in 3.8, so org-collector POSTs returned 503.
- **Home-account collector IRSA reads**: org-collector and incremental IRSA get the same collection actions as `SecurityGraphCollectorRole`. Home uses ambient credentials and has no spoke role.
- **Neptune ingest contention**: RULE-005 no longer uses `.times().until()` (two RepeatSteps, InternalFailure). Org-collector / compliance / rule-runner crons run every 4h, staggered. Graph-writer retries `ConcurrentModificationException` per vertex/reconcile and writes at concurrency 2. Collector fan-out matches that.

### Changed

- **CIEM graph access now uses SigV4 (completes the C1 auth item under D1)**:
  - `policy-evaluator` and `least-privilege-sweep` no longer read a Neptune password from Secrets Manager. They use the shared `NeptuneRuntimeClient`, signing with SigV4 exactly like graph-writer and the risk engine, so the execution role carries `neptune-db` permissions instead of `secretsmanager:GetSecretValue`
  - CDK: `PolicyEvaluatorRole` gets `neptune-db:ReadDataViaQuery`/`WriteDataViaQuery`; `LeastPrivilegeSweepRole` gets read only (its findings go to DynamoDB). `NEPTUNE_AUTH_SECRET_ARN` is gone from both functions
  - `NeptuneRuntimeClient` gained `bindings` pass-through and a `submit()` method that bypasses the instance result guard. The guard exists to stop unbounded reads from allocating without limit, but the CIEM lambdas deliberately page with `range()` and cap the total in `enumerateGraph`, so a legitimate page can exceed `maxResults` and would be rejected or truncated by `executeQuery`. `submit()` callers bound their own results; `executeQuery` keeps the guard
  - The Neptune auth secret resource is retained so the deployment does not delete a secret other tooling may reference; nothing in the stack can read it now. Removing it belongs to the data-protection workstream

- **Least-privilege IAM roles and scoped member assumption (D1 of the remediation plan)**:
  - CDK: the two shared execution roles are gone. `list-accounts`, `policy-evaluator`, `least-privilege-sweep`, `collector` and `incremental-collector` each get their own role with only the permissions they use. `list-accounts` no longer inherits the right to read the Neptune auth secret, which it never touches
  - CDK: hub `sts:AssumeRole` is limited to the approved `accountIds` and requires the configured `sts:ExternalId` condition, so the hub cannot even attempt an unapproved account. With no approved ids configured (organization-discovery deployments) the external ID condition still applies, and the resource stays a wildcard with a comment explaining why
  - Terraform: both `AssumeMemberCollector` statements in `khalifa-data` are scoped to `collection_account_ids` and carry the `sts:ExternalId` condition (from `random_password.collector_external_id`, marked `nonsensitive` because an external ID is a confused-deputy guard rather than a credential)
  - Terraform test asserts the scoped ARN, the external ID condition, and that the wildcard is gone

- **Scoring and compliance correctness (C2 of the remediation plan)**:
  - Compliance access-key controls now test the properties the collector actually writes and the risk rules already use: `1.10` (not rotated) uses `key_age_days`, `1.11` (unused) and the `A.9.2` composite use `last_used_days_ago`. Previously all three compared `last_used_date`, so `1.10` never flagged a long-lived but actively-used key and duplicated `1.11`
  - Risk scoring now populates `identityBlastRadius` from the CIEM properties on IAM roles (`is_admin`/`is_admin_role` → admin; `has_cross_account_trust` → cross-account), which were not projected before, so this 20%-weight factor was always zero
  - Removed the dead `cvss` factor: no vulnerability source feeds this system (`RULE-003` is disabled pending scanning), so the factor could only ever contribute zero while consuming 25% of the range. Weight is redistributed across exposure (0.3), identity (0.25), data classification (0.25) and environment (0.2). A finding with internet exposure, an admin identity, restricted data and a prod environment now reaches `critical` without needing a crown-jewel tag
  - `mergeDuplicateNodes` precedence is now explicit: a later stage only overrides a property when it supplies a defined value, so a later `undefined`/`null` can no longer erase what an earlier stage collected

- **CIEM fail-loud reads (C1 of the remediation plan)**:
  - `policy-evaluator` no longer swallows trust-edge and effective-permission read errors into empty lists: an empty result previously reported as "no escalation paths", indistinguishable from a healthy graph. A failed read now fails the run so the schedule and alarms see it
  - `least-privilege-sweep` distinguishes "no usage recorded" from "usage could not be read": a failed CloudTrail-usage read skips the principal (and increments a surfaced `usageUnavailable` count logged at error level) instead of treating it as zero usage, which produced recommendations to remove every action
  - `fetchUsedActions` accepts an injectable sender so the failure path is unit tested

- **CIEM query reshaping and bounding (B3 of the remediation plan)**:
